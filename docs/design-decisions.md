# Проектные решения безопасности — Cinema Booking

Решения для приоритетного набора угроз [модели угроз](threat-model.md): T-01, T-03, T-04, T-05, T-06. Требования — в [требованиях безопасности](security-requirements.md).

| Угроза | Требования | Решение |
| --- | --- | --- |
| T-01 | SR-01 | D-01 |
| T-03 | SR-03 | D-01 |
| T-04 | SR-05 | D-02 |
| T-05 | SR-04 | D-02 |
| T-06 | SR-08 | D-03 (опирается на D-02) |

Эти же решения закрывают угрозы среднего и низкого приоритета: T-02, T-09 и T-10 — D-01, T-07 — D-02. Для T-08 (SR-07) отдельное решение не принимается: сведения об отмене хранятся в записи бронирования, а их согласованность при одновременных отменах обеспечивает блокировка из D-02.

### D-01. Серверная проверка владельца и роли на основе проверенного токена

**Контекст:** все операции с бронированиями и административные операции вызываются через API, которое доступно напрямую, минуя интерфейс (TB-1). Скрытые кнопки не защищают от подстановки чужого `bookingId` (T-01), прямого вызова `/staff/*` зрителем (T-03), подстановки владельца в тело запроса (T-02) и подделки токена (T-09).

**Решение:**

- Web API принимает защищённые запросы только с access token Keycloak. Подпись проверяется по ключам Keycloak, а также проверяются издатель, получатель (`aud` нашего API) и срок действия. Допустимое расхождение часов уменьшено до 30 секунд.
- Идентификатор пользователя берётся только из claim `sub`, роль — только из ролей realm в токене (`realm_access.roles`). Роли Keycloak явно сопоставляются с ролями ASP.NET Core при проверке токена.
- По умолчанию доступ запрещён: глобальная fallback-политика требует аутентификации. Анонимный доступ явно разрешён только для `GET /health`, `/movies`, `/sessions`, `/sessions/{id}/seats` и, в окружении разработки, описания API `/openapi/v1.json`.
- Все административные операции находятся в одной группе маршрутов `/staff`, и политика «только роль сотрудника» назначается на всю группу, а не на отдельные методы.
- Операции зрителя с бронированием выбирают запись одним запросом сразу по `id` и владельцу (`WHERE id = @id AND user_id = @sub`). Чужое бронирование неотличимо от несуществующего, и сервер отвечает `404`.
- Модели запросов (DTO) не содержат полей владельца, роли и статуса. При создании бронирования владелец всегда равен `sub`. Модели ответов отделены от сущностей БД, поэтому список мест сеанса содержит только занятость места, без владельца (T-10).

**Обоснование:** решение о полномочиях принимает только сервер, и он проверяет каждый запрос (полное посредничество). Идентичность берётся из единственного доверенного источника — подписанного токена, поэтому подстановка `userId` в запросе или изменение claim роли ничего не дают. Запрет по умолчанию и политика на уровне группы `/staff` защищают от ошибки, когда новая административная операция добавлена без атрибута авторизации. Проверка владельца в самом запросе к БД исключает ситуацию «загрузили запись, но забыли проверить владельца». Ответ `404` вместо `403` не подтверждает существование чужого бронирования при переборе идентификаторов.

**Связанные угрозы:** T-01, T-03; также T-02, T-09, T-10.

**Связанные требования:** SR-01, SR-02, SR-03, SR-09.

**Будущая проверка:** опирается на критерии приёмки SR-01, SR-02, SR-03 и SR-09 и уточняет проверку механизма. Автоматизирована в [`AuthorizationTests`](../tests/CinemaBooking.Tests/AuthorizationTests.cs).

- **Условие:** в Keycloak есть зрители A и B и сотрудник S; у A есть активное бронирование; у B есть действительный токен.
- **Действие:**
  1. B вызывает `GET` и `DELETE /bookings/{id}` для бронирования A.
  2. B вызывает `POST /bookings`, добавив в тело `userId`/`ownerId` пользователя A.
  3. B вызывает `PATCH /staff/sessions/{id}`, `PATCH /staff/sessions/{id}/seats/{seatId}` и `DELETE /staff/bookings/{id}`.
  4. B отправляет токен с ролью `staff`, подписанный не ключом Keycloak (подпись не проходит проверку), токен с истёкшим сроком и токен, выданный для другого клиента Keycloak (`aud` не `cinema-api`).
  5. Любой пользователь вызывает `GET /sessions/{id}/seats`.
  6. Позитивные случаи: A просматривает и отменяет своё бронирование, S выполняет административную операцию.
- **Ожидаемый результат:**
  1. `404`, бронирование A в БД не изменилось.
  2. Создано бронирование с владельцем B.
  3. `403`, сеанс, места и бронирование не изменились.
  4. `401`, состояние не изменилось.
  5. Ответ не содержит идентификатора или имени владельца.
  6. Позитивные операции выполняются.
  
  Дополнительно автоматический тест обходит все зарегистрированные маршруты `/staff/*` и проверяет, что зритель на каждом получает `403`.

**Ограничения и последствия:**

- Изменение роли в Keycloak вступает в силу только после истечения уже выданного токена. Срок жизни access token должен оставаться коротким (по умолчанию в Keycloak 5 минут), отзыв токенов в реальном времени не реализуется.
- Решение полагается на корректную конфигурацию Keycloak и сопоставления ролей. Ошибка в сопоставлении приводит к отказу сотруднику во всех операциях (безопасный отказ), но не к выдаче прав зрителю.
- `404` на чужое бронирование усложняет диагностику для поддержки: факт «бронирование есть, но чужое» виден только в логах сервера.
- Каждая новая операция с бронированием обязана выбирать запись по `id` и владельцу. Это правило проверяется в ревью и тестах, а не обеспечивается автоматически.

### D-02. Атомарное создание бронирования под блокировкой сеанса и уникальность места в БД

**Контекст:** создание бронирования — это последовательность «проверить сеанс и места → записать бронирование». Если два запроса на одно место выполняются почти одновременно, оба могут увидеть место свободным (T-04). Если места обрабатываются по одному, отказ на одном из них оставляет частичное бронирование (T-07). Сотрудник может одновременно отменить сеанс или заблокировать место, и бронирование создаётся по устаревшему состоянию (T-05). Проверка в интерфейсе не помогает, потому что запрос можно отправить напрямую.

**Решение:**

- `POST /bookings` выполняется в одной транзакции PostgreSQL. Первым действием строка сеанса блокируется: `SELECT ... FROM sessions WHERE id = @sessionId FOR UPDATE`.
- Под этой блокировкой сервер проверяет:
  - сеанс не отменён и бронирование на него не закрыто;
  - все `seatIds` относятся к залу сеанса;
  - все места доступны (не заблокированы сотрудником);
  - на места нет активных бронирований.

  Затем одним действием создаются бронирование и все строки `booking_seats`. Любая неудача откатывает транзакцию целиком.
- Административные операции, которые меняют состояние сеанса или доступность мест, берут ту же блокировку строки сеанса. Поэтому они выполняются либо до, либо после бронирования, но не одновременно с ним.
- Отмена бронирования — владельцем или сотрудником — тоже берёт блокировку сеанса и проверяет, что бронирование ещё активно, уже под ней. При реализации выяснилось, что без этого одновременные отмены владельцем и сотрудником проходят обе, и вторая перезаписывает сведения об отмене: запись SR-07 может приписать отмену не тому исполнителю.
- Второй барьер — в схеме БД: в `booking_seats` хранится `session_id` и признак активности, а частичный уникальный индекс `UNIQUE (session_id, seat_id) WHERE is_active` не позволяет сохранить два активных бронирования одного места. Нарушение индекса сервер превращает в `409 Conflict`.

**Обоснование:** свойство «одно место — одно активное бронирование» обеспечивает БД, а не порядок действий в коде. Рассмотрены три варианта:

| Вариант | Что обеспечивает | Чего не обеспечивает |
| --- | --- | --- |
| Только уникальный индекс | Исключает двойное бронирование места даже при ошибке в коде | Не учитывает гонку с отменой сеанса или блокировкой места сотрудником (T-05) и лимит на зрителя (T-06, D-03): эти условия не выражаются уникальностью |
| Уровень изоляции `SERIALIZABLE` | Все проверки корректны без явных блокировок | При конкуренции транзакции откатываются с ошибкой сериализации, и сервер обязан повторять запрос. Поведение при повторах сложнее воспроизвести и проверить |
| **Блокировка строки сеанса + уникальный индекс (выбрано)** | Все проверки сеанса, мест и лимита выполняются над согласованным состоянием, запросы на один сеанс просто встают в очередь | Бронирования на один сеанс выполняются строго последовательно |

Последовательная обработка в рамках одного сеанса допустима: в зале не больше нескольких сотен мест, а транзакция бронирования короткая. Уникальный индекс оставлен как страховка на случай операции, которая по ошибке не возьмёт блокировку.

**Пересмотреть выбор**, если очередь на блокировку сеанса станет заметной на нагрузке (например, старт продаж на премьеру) или если состояние мест будет вынесено из PostgreSQL (кэш в Redis, обработка через Kafka). Тогда блокировка строки перестанет охватывать всё состояние.

**Связанные угрозы:** T-04, T-05; также T-07, T-08.

**Связанные требования:** SR-04, SR-05, SR-06.

**Будущая проверка:** опирается на критерии приёмки SR-04, SR-05 и SR-06 и уточняет проверку конкурентного поведения. Автоматизирована в [`BookingConsistencyTests`](../tests/CinemaBooking.Tests/BookingConsistencyTests.cs).

- **Условие:** тестовая БД PostgreSQL (не in-memory, иначе блокировки и частичный индекс не проверяются); сеанс с местами 1–10; у зрителей A и B действительные токены.
- **Действие:**
  1. 20 параллельных `POST /bookings` от A и B на место 5, запущенных одновременно через барьер.
  2. Запрос на места 3, 4 и 99, где место 99 из другого зала.
  3. Параллельно `PATCH` сотрудника, который отменяет сеанс, и `POST /bookings` на этот сеанс.
  4. Прямая вставка в `booking_seats` второй активной строки для места 5 в обход API.
  5. Одновременная отмена одного бронирования владельцем и сотрудником (с причиной).
- **Ожидаемый результат:**
  1. Ровно один ответ `201`, остальные `409`; в БД одно активное бронирование места 5.
  2. Отказ, места 3 и 4 остались свободными, бронирование не создано.
  3. После завершения обоих запросов нет активного бронирования на отменённый сеанс, созданного после отмены.
  4. Ошибка нарушения уникальности.
  5. Успешна ровно одна отмена, вторая получает `409`; исполнитель, признак отмены сотрудником и причина в записи соответствуют прошедшей операции.

**Ограничения и последствия:**

- Пропускная способность бронирования на один сеанс ограничена одной транзакцией за раз.
- Все операции, меняющие сеанс и места, обязаны брать блокировку в одном порядке («сначала сеанс»), иначе возможны взаимные блокировки.
- Отмена бронирования снимает признак `is_active` у его мест в той же транзакции.
- Решение проверяемо только на настоящем PostgreSQL. In-memory провайдер для этих тестов не подходит.

### D-03. Лимит мест на зрителя проверяется в транзакции бронирования

**Контекст:** бронирование бесплатно, и один зритель может занять большую часть зала одним длинным `seatIds[]` или серией запросов (T-06). При проработке решения выяснилось, что первоначальная схема «прочитать число мест зрителя на сеансе → сравнить с лимитом → создать бронирование» нарушается параллельными запросами. Два запроса по 4 места оба видят «0 из 6» и оба проходят, итого 8 мест. Поэтому в критерий SR-08 добавлено условие одновременных запросов, а проверка лимита перенесена под блокировку D-02.

**Решение:**

- Лимиты задаются в конфигурации сервера (`Booking` в `appsettings.json`), а не в запросе: не больше 6 мест в одном бронировании и не больше 6 мест в активных бронированиях одного зрителя на одном сеансе.
- Длина `seatIds[]` проверяется до обращения к БД. Суммарный лимит проверяется внутри транзакции D-02, после блокировки строки сеанса: число активных мест зрителя на сеансе (`booking_seats` по `session_id` и `is_active`, соединённые с `bookings` по владельцу `@sub`). Превышение откатывает транзакцию и возвращает `422` с понятной причиной.
- Отменённые бронирования в лимит не входят: после отмены зритель снова может бронировать.

**Обоснование:** блокировка строки сеанса из D-02 уже упорядочивает все бронирования сеанса. Поэтому подсчёт мест зрителя под ней видит актуальное значение без отдельного механизма. Счётчик в отдельной таблице или в Redis потребовал бы своей синхронизации и создал бы второе место, где может появиться та же гонка. Лимит в конфигурации позволяет менять значения без изменения кода.

**Связанные угрозы:** T-06.

**Связанные требования:** SR-08.

**Будущая проверка:** опирается на критерий приёмки SR-08. Автоматизирована в [`BookingLimitTests`](../tests/CinemaBooking.Tests/BookingLimitTests.cs).

- **Условие:** лимит 6; у зрителя A на сеансе нет бронирований; используется тестовая PostgreSQL, как в D-02.
- **Действие:**
  1. A отправляет одно бронирование на 7 мест.
  2. A отправляет два параллельных запроса по 4 места на разные свободные места.
  3. A бронирует 6 мест, отменяет одно бронирование и снова бронирует.
- **Ожидаемый результат:**
  1. Отказ, места не заняты.
  2. Успешен ровно один запрос, у A на сеансе 4 активных места.
  3. После отмены повторное бронирование в пределах лимита проходит.

**Ограничения и последствия:**

- Лимит действует на учётную запись, а не на человека. Захват зала через несколько учётных записей остаётся принятым остаточным риском T-06 (см. [модель угроз](threat-model.md)); компенсирующая мера — отмена массовых бронирований сотрудником (SR-03, SR-07).
- Лимит может мешать законному групповому бронированию больше чем на 6 мест. Таким группам придётся обращаться к сотруднику.
- Решение не работает без D-02: если бронирование перестанет брать блокировку сеанса, гонка лимита вернётся.
